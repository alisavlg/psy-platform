# PsyHelp — Роли, права и делегирование

**Версия:** 4.2
**Последнее обновление:** 24 сентября 2026

---

## 1. Главный принцип

- **У собственника есть ВСЕ права по умолчанию.**
- Остальные роли **не имеют прав по умолчанию** — они получают их от собственника.
- Собственник может:
  1. **Назначать права ролям** (долгосрочно).
  2. **Ставить задачи конкретным людям** (разово).
- Собственник может **забрать** любое право или задачу в любой момент.

Это называется **гибкая система прав + делегирование задач**.

---

## 2. Список ролей

| Роль | Краткое описание |
|------|------------------|
| **Гость** | Незарегистрированный посетитель |
| **Клиент** | Ищет психолога, записывается, оплачивает, общается |
| **Психолог** | Оказывает услуги, ведёт расписание, публикует статьи |
| **Модератор** | Выполняет задачи по модерации |
| **Администратор** | Выполняет задачи по управлению |
| **Собственник** | Владелец платформы |

**Примечание:** один человек может иметь **несколько ролей**.

## 3. Хранение в базе данных

### 3.1. `roles` — список ролей

| Поле | Тип | Описание |
|------|-----|----------|
| id | INTEGER | Уникальный ID |
| name | VARCHAR | client / psychologist / moderator / admin / owner |
| description | TEXT | Описание |
| is_system | BOOLEAN | Системная роль (нельзя удалить) |

### 3.2. `permissions` — список всех возможных действий

| Поле | Тип | Описание |
|------|-----|----------|
| id | INTEGER | Уникальный ID |
| code | VARCHAR | Уникальный код (например, `conduct_interview`) |
| name | VARCHAR | Название |
| category | VARCHAR | Категория (moderation, content, admin) |

**Примеры прав:**

| code | name |
|------|------|
| `view_profiles` | Смотреть профили |
| `book_session` | Записываться на сессию |
| `conduct_session` | Проводить сессии |
| `publish_article` | Публиковать статьи |
| `moderate_chat` | Модерировать чаты |
| `verify_psychologist` | Проверять психологов |
| `conduct_interview` | Проводить собеседования |
| `ban_user` | Банить пользователей |
| `manage_roles` | Управлять ролями |

### 3.3. `role_permissions` — какие права у роли (долгосрочно)

| Поле | Тип | Описание |
|------|-----|----------|
| id | INTEGER | Уникальный ID |
| role_id | INTEGER | Ссылка на `roles.id` |
| permission_id | INTEGER | Ссылка на `permissions.id` |
| granted_by | INTEGER | Кто дал право |
| granted_at | TIMESTAMP | Когда дано |

**Редактирует собственник.**

Пример начальной настройки:

| role | permissions |
|------|-------------|
| client | `view_profiles`, `book_session` |
| psychologist | `conduct_session`, `publish_article` |
| moderator | `moderate_chat` |
| admin | (пусто — получает задачи) |

### 3.4. `user_roles` — какие роли у пользователя

| Поле | Тип | Описание |
|------|-----|----------|
| id | INTEGER | Уникальный ID |
| user_id | INTEGER | Ссылка на `users.id` |
| role_id | INTEGER | Ссылка на `roles.id` |
| assigned_by | INTEGER | Кто назначил |
| assigned_at | TIMESTAMP | Когда назначена |

**Важно:** роли хранятся только здесь. В таблице `users` поля `role` нет.

### 3.5. `tasks` — делегированные задачи (разово)

| Поле | Тип | Описание |
|------|-----|----------|
| id | INTEGER | Уникальный ID |
| author_id | INTEGER | Кто поставил задачу |
| assignee_id | INTEGER | Кому поручено |
| type | VARCHAR | verify_psychologist / interview / moderation_review / custom |
| title | VARCHAR | Заголовок |
| description | TEXT | Описание |
| target_user_id | INTEGER | С кем работаем (например, психолог) |
| application_id | INTEGER | Ссылка на `applications.id` (если задача по заявке) |
| checklist | JSON | Чек-лист инструкции: массив `{id, text, checked, comment}` |
| recommendation | VARCHAR | Рекомендация исполнителя: approve / reject / request_changes / request_documents |
| recommendation_reason | TEXT | Аргументация исполнителя |
| final_decision | VARCHAR | Решение собственника: approved / rejected / needs_changes / needs_documents |
| final_decision_reason | TEXT | Комментарий собственника клиенту |
| decided_by | INTEGER | Кто принял финальное решение |
| decided_at | TIMESTAMP | Когда принято финальное решение |
| status | VARCHAR | in_progress / awaiting_decision / completed / cancelled |
| created_at | TIMESTAMP | Когда создана |
| completed_at | TIMESTAMP | Когда выполнена |

## 4. Как это работает на практике

### Сценарий 1. Собственник даёт право роли (долгосрочно)

**Задача:** «Модератор должен всегда мочь модерировать чаты».

1. Собственник заходит в админ-панель.
2. Открывает «Управление ролями».
3. Даёт роли `moderator` право `moderate_chat`.
4. Запись сохраняется в `role_permissions`.
5. Теперь **все** модераторы могут модерировать чаты — пока собственник не заберёт право.

### Сценарий 2. Собственник ставит задачу (разово)

**Задача:** «Проверить заявку психолога Иванова».

1. Психолог Иванов регистрируется, присылает документы.
2. Заявка попадает в `applications` со статусом `pending`.
3. Собственник открывает админку, видит заявку.
4. Собственник нажимает «Делегировать», выбирает модератора Петрова.
5. Система создаёт задачу в `tasks`:
   - тип `verify_psychologist`,
   - исполнитель — Петров,
   - объект — Иванов,
   - чек-лист из шаблона (6 пунктов: диплом, сертификаты, стаж, собеседование, описание, правила),
   - статус `in_progress`.
6. Заявка переходит в `in_review`.
7. Петров видит задачу в кабинете, проходит по пунктам чек-листа, отмечает галочки, пишет комментарии.
8. Пишет рекомендацию: `approve` + аргументацию.
9. Отправляет собственнику — задача переходит в `awaiting_decision`.
10. Собственник видит чек-лист, комментарии и рекомендацию.
11. Принимает **финальное решение** — `approved` / `rejected` / `needs_changes` / `needs_documents`.
12. Если `approved` — Иванову добавляется роль `psychologist`, ему уходит уведомление.

**Важно:** модератор **не решает** — он рекомендует и аргументирует. Финальное решение всегда за собственником.

## 5. Матрица прав (начальная)

**Жёсткой матрицы нет.** Всё определяется:
- `role_permissions` — долгосрочные права ролей.
- `tasks` — разовые задачи.

**Начальная настройка (предложение):**

| Действие | Гость | Клиент | Психолог | Модератор | Админ | Собственник |
|----------|:-----:|:------:|:--------:|:---------:|:-----:|:-----------:|
| Смотреть публичные страницы | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Регистрация | ❌ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Записаться на сессию | ❌ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Проводить сессии | ❌ | ❌ | ✅ | ❌ | ✅ | ✅ |
| Публиковать статьи | ❌ | ❌ | ✅ | ❌ | ✅ | ✅ |
| Отвечать в Q&A | ❌ | ❌ | ✅ | ❌ | ✅ | ✅ |
| Модерировать чаты | ❌ | ❌ | ❌ | ✅ | ✅ | ✅ |
| Проверять психологов | ❌ | ❌ | ❌ | ⚠️ (по задаче) | ⚠️ (по задаче) | ✅ |
| Проводить собеседования | ❌ | ❌ | ❌ | ⚠️ (по задаче) | ⚠️ (по задаче) | ✅ |
| Банить пользователей | ❌ | ❌ | ❌ | ❌ | ✅ | ✅ |
| Управлять ролями | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ |

**Обозначения:**
- ✅ — есть право
- ❌ — нет права
- ⚠️ — может получить по задаче от собственника

## 6. Особые правила

### 6.1. Собственник — единственный, у кого все права

Никто другой не имеет всех прав. Даже администратор. Только собственник.

### 6.2. Делегирование — это задача, а не роль

Когда собственник «делегирует» что-то администратору — он ставит **задачу**. Это не меняет роль администратора. Просто у него появляется конкретное поручение.

### 6.3. Анонимность и защита контактов

**Принцип нулевого доверия между сторонами:**
Клиент и психолог **не имеют доступа к личным контактам друг друга**. Всё общение — **только через платформу**.

- Все работают под **именем и отчеством** (без фамилии). Фамилия — только в закрытом реестре.
- **Психолог не видит** телефон, email и фамилию клиента.
- **Клиент не видит** телефон, email и фамилию психолога.
- **Все коммуникации** — только через внутренние инструменты платформы: чат, видеосессии, заявки.
- **Только администратор** имеет доступ к контактам обеих сторон — для решения спорных ситуаций и юридических вопросов.
- Это правило **нельзя обходить** — ни ролям, ни задачам, ни делегированию.

**Зачем это нужно:**
- Исключает утечку клиентов с платформы (психолог не уведёт клиента в мессенджер).
- Обеспечивает конфиденциальность персональных данных.
- Гарантирует, что все транзакции и коммуникации идут через платформу.

### 6.4. Несколько ролей

Один пользователь может иметь несколько ролей. Права **суммируются**.

### 6.5. Репутация психолога

- **Звёзды** — от клиентов после проведённых сессий.
- **Один клиент — один отзыв** на психолога.
- **Рейтинг пересчитывается** при каждом новом отзыве.
- **Уровни** — по стажу (от даты начала практики).
- **Звёзды можно снимать** за нарушения (модерация).

### 6.6. Психолог может быть клиентом другого психолога

Один пользователь может одновременно иметь роли `psychologist` и `client`.

**Пример:**
- Анна — практикующий психолог. Она сама ходит на сессии к психологу Ивану.
- В системе у Анны две роли: `psychologist` и `client`.
- В мессенджере она общается с Иваном как клиент, а со своими клиентами — как психолог.

**Особый случай:** уведомления при отмене сессии.
Если один человек — и клиент, и психолог на одной сессии, — ему приходит **одно** уведомление, а не два.

### 6.7. Изоляция данных пользователей

Данные каждого пользователя **строго изолированы**:
- Чаты — у каждого свои.
- Календарь и планировщик — личные.
- Сессии, заметки, профиль — только у владельца.

Один пользователь **не видит** данные другого.

**В прототипе** (до backend) изоляция реализована через суффикс `_<user_id>` в ключах localStorage:
- `psyhelp_events_<user_id>` — календарь пользователя.
- `psyhelp_sessions_<user_id>` — сессии пользователя.
- `psyhelp_notifications_<user_id>` — уведомления.

**Ключевой принцип:** ключ строится по `user.id`, **а не по роли**. Один человек в ролях клиента и психолога видит один и тот же календарь.

После перехода на backend — на таблицы `events`, `sessions`, `notifications` с фильтром по `user_id`.

## 7. Правила работы с задачами

### 7.1. Уведомления

- При создании задачи исполнитель получает уведомление (email + в системе).
- При изменении статуса автор получает уведомление.
- При завершении задачи автор получает уведомление с комментарием исполнителя.

### 7.2. Дедлайны

- Дедлайн **желателен, но не жёсткий**.
- Исполнитель может указать предполагаемую дату выполнения.
- Если задача связана с внешним человеком (например, собеседование с психологом) — исполнитель сам связывается и согласовывает дату и время.
- Система напоминает исполнителю, если дедлайн близко или просрочен.

### 7.3. Логирование

- Все действия по задачам логируются:
  - Кто создал задачу.
  - Кому назначена.
  - Когда изменён статус.
  - Какой комментарий оставлен.
- Логи доступны собственнику и администраторам.

### 7.4. Отклонение задач

- Исполнитель **не может отказаться** от задачи.
- Если не может выполнить — пишет комментарий автору, автор переназначает другому.
- Задача не может оставаться в статусе `in_progress` бесконечно.

### 7.5. Статусы задач

| Статус | Описание |
|--------|----------|
| `in_progress` | Исполнитель взял в работу |
| `awaiting_decision` | Исполнитель отправил рецензию, ждёт решения собственника |
| `completed` | Собственник принял финальное решение |
| `cancelled` | Отменена автором |

**Ключевой принцип:** исполнитель **не принимает решений**. Он собирает доказательства, отмечает пункты чек-листа и пишет рекомендацию. Финальное решение всегда за собственником.

### 7.6. Варианты финального решения

| Решение | Что означает | Что видит клиент |
|---------|--------------|------------------|
| `approved` | Одобрено | Роль психолога активна |
| `rejected` | Отклонено | Комментарий с причиной |
| `needs_changes` | Запросить изменения | Комментарий: что поправить |
| `needs_documents` | Запросить документы | Комментарий: что догрузить |

После `rejected` / `needs_changes` / `needs_documents` клиент может **исправить заявку и подать заново**.

## 8. Реализация в коде и преимущества

### 8.1. Как это работает

1. **При регистрации** пользователь получает роль `client`.
2. **Собственник** через админ-панель:
   - Управляет `role_permissions` (долгосрочные права).
   - Создаёт задачи в `tasks` (разовые поручения).
3. **При каждом действии** сервер проверяет:
   - Есть ли у пользователя право (через роли)?
   - Или у него есть задача, дающая это право?
4. **На фронтенде** — скрываем недоступное.
5. **На бэкенде** — обязательно проверяем.

**Пример:**

Модератор пытается отправить рецензию по заявке.

    Сервер: у роли moderator есть право conduct_interview? → Нет.
    Сервер: есть ли у него активная задача типа verify_psychologist? → Да, для психолога Иванова.
    Сервер: разрешает действие.

### 8.2. Преимущества модели

- **Гибкость** — собственник управляет всем.
- **Масштабируемость** — новые роли и задачи добавляются без переписывания кода.
- **Делегирование** — можно передать задачу, не давая права навсегда.
- **Контроль** — собственник всегда видит, кто что делает.
- **Безопасность** — контакты сторон скрыты, утечка клиентов исключена.
- **Конфиденциальность** — вся коммуникация через платформу.
